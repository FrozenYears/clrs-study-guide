## 三、怎么核对一条，怎么改一条

### 第 1 步：把题干和提示并排打出来看

```powershell
python tools/_probe/ex_show.py 13.2-3 16.1-1 12.2-1
```

一次多给几个题号。它输出「原书题干 + 本站提示」，这就是你判断对错的唯一依据。

### 第 2 步：判断是否真的错了

清单给的证据可能不准。要判的只有一件事：**这段提示是不是在帮学生做它上面那道题**。四类算真错：

- 题干问 A，提示讲 B；
- 提示给的结论和题干要求矛盾（复杂度、方向、下标基准、正负号）；
- 提示引用的定理号/图号/性质号/页码与原书不符；
- 提示说「回阶段 N 看某个东西」，但那一阶段里根本没有那样东西。

不算错的：中文风格、标点、长度、数学写法（提示会走公式渲染，`$…$` 合法）。

### 第 3 步：改

写一个 JSON，格式是 `{文件路径: {题号: 新提示文本}}`，然后：

```powershell
python tools/_probe/hint_io.py apply tools/_probe/你的批次.json
```

它只替换 `hint` 字段，不碰题干和页码。改完对每个动过的文件跑一次 `node --check <文件>`。

### 第 4 步：验收（四条都要过）

```powershell
node tools/dump_levels.mjs
python tools/04_verify_level.py            # 期望 0 ERROR / 0 WARN，且关卡数仍是 152
python tools/09_audit_book_exercises.py    # 期望 600 道全逐字
cd site; node assets/core/__tests-katex__.mjs   # 期望 83 passed
```

全绿再提交。一批建议 15–25 条，一次提交，提交信息里写清**每条为什么是错的**（这是本项目唯一能追溯判断依据的地方）。

## 四、坑（每一条都是真踩过的，别再踩）

1. **分头检查的助手会编造问题。** 上一轮七个助手分头读提示，其中一个报了 6 条「这段提示整体是别的题的」。我逐条核对，**6 条全是假的**——那些提示本来就对；它还引用了两个站内根本不存在的题号（`7.4-5`、`10.4-1`）。所以清单只能当线索，改之前必须自己看原文。

2. **助手给的修法方向可能正好相反。** 另一个助手建议「把 25 条提示里的阶段号统一减 1」。实际根因在显示端：路由是 1 基、侧栏链接是 1 基、只有页面显示的段号用了 0 基。统计过 266 处文案：109 处按 1 基写、31 处按 0 基写。**改的是显示，不是文案**。凡是「批量机械修正」的建议，先数一遍全站再动手。

3. **段号现在统一是 1 基**：`0=位置感` 那套已经废弃。现在页面上：1 位置感、2 直觉入口、3 原文精读、4 伪代码骨架、5 动手看见、6 双轨实现、7 复杂度、8 正确性、9 闯关测验。清单里凡是抱怨「阶段号差 1」的条目，**先确认它是不是已经随着显示修正而不再是问题**（第 32 轮报告里那批「指路错误」大部分已经自动消失了）。

4. **有些字段不走公式渲染，放了 `$…$` 就会把反斜杠和美元符原样显示在页面上**：
   `stage.title`、`pseudocode.more[].subtitle`、`pseudocode.vars[].name`、`prove.steps[].title`、`analyze.figureTitle`、`visualize.presets[].name`、`map.unlocks[].label`、`prerequisites[].label`、表格与图表的 `caption`。
   要写数学就用 Unicode（`Θ(n lg n)`、`n²`、`≥10¹⁸`）。自查：`python tools/_probe/round32_scan.py tex`。

5. **一个没配对的 `$` 会把后半句整个吞进公式模式**（渲染器遇到未闭合的 `$` 会一路吃到字符串结尾）。`python tools/_probe/round32_scan.py tex` 也会查这个。

6. **表格只渲染两列。** `kvTable` 取每行的 `r[0]`（行首）、`r[1]`（单元格），`r[2]` 只是「等宽显示」的开关。写三列以上的表，第三列会被静默丢掉。

7. **图表的 `expr` 只能是一个 JS 表达式**（内部是 `new Function('n', 'return ' + expr)`），变量名是 `n`。写成 `let f=1; for(...); return f;` 会语法错误——**而且页面不报错、只是整块空白**，只能靠全量页面检查发现。

8. **改 `hint` 之外不要顺手改别的字段。** 题干（`statement`）和页码（`page`）由 `tools/10_sync_book_exercises.py` 从语料生成，手改会造成与原文不一致。

9. **写正则处理关卡文件时注意两种写法**：有的记录挤成一行，有的字段各占一行；`page` 可能是 `[33, 34]` 这种区间。正则没吃下中括号里的逗号，就会**静默漏掉整条记录**（上一轮因此漏了 2 条，靠「扫描条数 vs 实际条数」对不上才发现）。改完一定要数一遍命中条数是否等于预期。

10. **`tools/_probe/` 是 gitignore 的**，里面是本文档引用的常用工具（`ex_show.py`、`hint_io.py`、`round32_scan.py`、`star_render.py`、`stage_ref_scan.py`、`r33_recheck_with_smoke.py` 等）。**不要批量清理这个目录**——删了找不回来（上一轮真丢过 10 个）。

11. **不要同时开多个无头 Chrome 探针**，会互相干扰出现假失败；必须串行，且带 `--virtual-time-budget=20000`。DOM 只有 1.3KB 左右说明页面根本没渲染出来，别当成站点 bug。

12. **新引入的 LaTeX 命令必须是渲染器认识的**，否则页面上会出现 `\textfor` 这种碎片，不报错。第 3 步那条 `__tests-katex__` 检查就是拦这个的。

13. **Git Bash 的 PATH 是坏的**（`ls`/`head`/`grep` 之类可能不可用）。文件操作用绝对路径或直接用 Read/Write/Grep 工具。Python 内联 `-c` 里的反斜杠会被吃掉，**脚本一律写成文件再跑**。
